# TFLite Hook

Implementation of the ML encryption hook for TensorFlow Lite models.

## Overview

This directory contains the TensorFlow Lite-specific implementation of the encryption hook mechanism, based on the TensorRT reference implementation. Like ONNX Runtime, TFLite loads its model format (a FlatBuffer) directly from bytes — no intermediate conversion is needed.

Unlike the other three frameworks, TFLite has no official precompiled C++ package: it must be built from source. This is also the only framework in this toolkit with two validated hook implementations — a primary one targeting the stable public C API, and a second one targeting an internal C++ symbol. See "Two hooks" below.

## Structure

```
tflite/
├── README.md                         # This file
├── install_requirements.sh           # Clones TensorFlow and builds the TFLite subset via CMake
├── src/                               # All source code and the build system
│   ├── Makefile
│   ├── compile_tflite.cpp            # Encrypts a raw .tflite file (AES-256-ECB)
│   ├── infer_tflite.cpp              # Loads the encrypted model, decrypts it in memory, runs inference
│   ├── tflite_model_create_hook.c    # Primary hook (C API): dumps the decrypted model
│   └── tflite_model_create_hook_cxx.cpp # Secondary hook (internal C++ symbol) — see "Two hooks" below
├── build/                             # Compiled binaries (generated, not tracked by git)
│   ├── compile_tflite
│   ├── infer_tflite
│   ├── tflite_model_create_hook.so
│   └── tflite_model_create_hook_cxx.so
└── models/                            # All model files, at every stage (kept in git via .gitkeep)
    ├── .gitkeep
    ├── model.tflite                   # Input model (source, not versioned)
    ├── model.tflite.enc                # Encrypted model (generated)
    ├── dumped_model.tflite             # Stolen model, via the C hook (generated by the attack)
    └── dumped_model_cxx.tflite         # Stolen model, via the C++ hook (generated by the attack)
```

`src/` holds only code, `build/` holds only compiled binaries (git-ignored), and `models/` holds every model artifact — regardless of which stage produced it. `models/.gitkeep` keeps the empty folder tracked in git even before any artifact has been generated. Conversion byproducts (e.g. an `onnx2tf` output folder, `.fbs` schema, tensor correspondence reports) are not part of the toolkit and are git-ignored — only `model.tflite` is the actual toolkit input.

## Requirements

- Linux x86_64
- `g++` / `gcc` with C++17 support, `make`, and `cmake`
- TensorFlow Lite C API, built from source (no official precompiled C++ package exists)
- OpenSSL development headers (`libssl-dev`)

Run the install script from the `tflite/` directory to install everything above in one go:

```bash
./install_requirements.sh
```

This clones TensorFlow (`v2.18.0`, shallow clone) into `~/Downloads/tensorflow`, then builds the TFLite subset via CMake into `~/Downloads/tflite_build`, with `-DBUILD_SHARED_LIBS=ON` (required: without it, CMake only produces static `.a` libraries, which cannot be targeted with `LD_PRELOAD`) and XNNPACK enabled.

If TensorFlow is built elsewhere, adjust `TFLITE_SRC` and `TFLITE_BUILD_LIB` at the top of `src/Makefile`.

**FlatBuffers headers**: the C++ hook (`tflite_model_create_hook_cxx.cpp`) additionally needs FlatBuffers headers, which CMake fetches as a build dependency rather than exposing where you'd expect. If you hit `fatal error: flatbuffers/base.h: No such file or directory`, locate the real path with:
```bash
find ~/Downloads/tflite_build -name "base.h" 2>/dev/null | head -1
```
and point `FLATBUFFERS_INC` in `src/Makefile` at its parent `include/` directory — on this setup it resolved to `$(TFLITE_BUILD_LIB)/flatbuffers/include`, not the `_deps/flatbuffers-src/include` path CMake's own build tree structure might suggest.

### Getting a test model

This repository does not version any model file. TFLite doesn't load `.onnx` directly, so convert one first:

```bash
pip install onnx2tf tensorflow onnx onnxruntime onnx_graphsurgeon --break-system-packages
onnx2tf -i your_model.onnx -o converted_model -osd
cp converted_model/model_float32.tflite models/model.tflite
```

## Build & run (via Makefile)

All commands below are run from `tflite/src`. Compiled binaries are placed in `../build`, which is git-ignored — nothing under `build/` should be committed.

```bash
make all           # compiles compile_tflite, infer_tflite, and the C API hook into ../build
make run-baseline  # encrypts ../models/model.tflite, runs inference normally (no attack)
make run-attack    # encrypts the model, runs the attack, dumps the stolen model to ../models/
make clean         # removes ../build entirely
```

Override the password or the input model without editing the `Makefile`:

```bash
make run-attack PASSWORD=yourpassword MODEL=../models/other_model.tflite
```

`tflite_model_create_hook_cxx.cpp` is intentionally **not** built by `make all` — build it explicitly with:

```bash
make hook-cxx-experimental
```

### What each target does

- **`compile_tflite`**: reads `model.tflite`, encrypts it with AES-256-ECB, and writes it to `../models/model.tflite.enc`.
- **`infer_tflite`**: reads `model.tflite.enc`, decrypts it in RAM, and calls `TfLiteModelCreate(model_data, model_size)` to load and run inference — this is the legitimate, non-hooked path.
- **`tflite_model_create_hook.so`**: the `LD_PRELOAD` library used in `make run-attack`. It intercepts `TfLiteModelCreate` and dumps the decrypted model to `../models/dumped_model.tflite` before letting the real function proceed.
- **`tflite_model_create_hook_cxx.so`**: the alternative C++-level hook (see "Two hooks" below), built by `make hook-cxx-experimental`. Dumps to `../models/dumped_model_cxx.tflite`.

## Troubleshooting / Quirks

- TensorFlow Lite must be built with shared libraries enabled (`BUILD_SHARED_LIBS=ON`) for `LD_PRELOAD` to work.
- The C API hook is the primary supported path; the C++ hook is experimental and may depend on specific TFLite exports.
- If the model fails to load, verify `LD_LIBRARY_PATH` and the location of the TensorFlow Lite shared library.

## Manual build (if you're not using `make`)

```bash
cd src
mkdir -p ../build

g++ -std=c++17 compile_tflite.cpp -o ../build/compile_tflite -lcrypto

g++ -std=c++17 infer_tflite.cpp -o ../build/infer_tflite \
    -I$HOME/Downloads/tensorflow \
    -L$HOME/Downloads/tflite_build \
    -Wl,-rpath,$HOME/Downloads/tflite_build \
    -ltensorflow-lite -lcrypto

gcc -shared -fPIC tflite_model_create_hook.c -o ../build/tflite_model_create_hook.so -ldl

# C++ hook (optional, see "Two hooks"):
g++ -std=c++17 -shared -fPIC tflite_model_create_hook_cxx.cpp -o ../build/tflite_model_create_hook_cxx.so \
    -I$HOME/Downloads/tensorflow \
    -I$HOME/Downloads/tflite_build/flatbuffers/include \
    -L$HOME/Downloads/tflite_build \
    -Wl,-rpath,$HOME/Downloads/tflite_build \
    -ltensorflow-lite -ldl
```

## Run manually, step by step

```bash
cd src
mkdir -p ../models   # first run only
export LD_LIBRARY_PATH=$HOME/Downloads/tflite_build:$LD_LIBRARY_PATH

../build/compile_tflite ../models/model.tflite model.tflite.enc <password>
../build/infer_tflite ../models/model.tflite.enc <password>
LD_PRELOAD=../build/tflite_model_create_hook.so ../build/infer_tflite ../models/model.tflite.enc <password>
```

The decrypted model is dumped to `../models/dumped_model.tflite`, byte-for-byte identical to the original `.tflite` file — despite the on-disk file being encrypted. Verify with:

```bash
diff ../models/dumped_model.tflite ../models/model.tflite
# (no output means the files are identical)
```

## How it works (primary hook)

1. `infer_tflite` reads the encrypted `.tflite.enc` file and decrypts it in RAM (AES-256-ECB, key derived from the password via SHA-256).
2. It calls `TfLiteModelCreate(model_data, model_size)`, the TFLite C API's entry point for loading a model from an in-memory buffer.
3. `TfLiteModelCreate` is a plain, exported C function — no C++ name mangling, no vtable indirection to walk. This makes it the simplest interception target of the four frameworks in this toolkit: the hook doesn't need to parse an ABI-specific mangled symbol name or patch a struct of function pointers, it just needs to shadow the symbol directly, exactly like the very first `printf` proof of concept this toolkit's approach was built on.
4. The hook defines its own `TfLiteModelCreate` and is loaded before `libtensorflow-lite.so` via `LD_PRELOAD`, so the dynamic linker resolves calls to it first. It resolves the real implementation with `dlsym(RTLD_NEXT, "TfLiteModelCreate")`, dumps the decrypted model buffer to disk, then forwards the call to the real function so the program behaves normally and the victim notices nothing.

## Two hooks: why this framework has both a C and a C++ implementation

Investigating a C++-level hook (mirroring the ONNX Runtime experiment) led to a different, more nuanced finding than for ONNX Runtime:

- **ONNX Runtime**: `Ort::Session`'s constructor is `inline`, compiled directly into the caller. No dynamic symbol for it exists anywhere — hooking it is structurally impossible, not just hard.
- **TFLite**: the internal `tflite::impl::FlatBufferModelBase<FlatBufferModel>::VerifyAndBuildFromAllocation` **is** exported as a weak dynamic symbol (confirmed with `nm -D libtensorflow-lite.so | grep VerifyAndBuildFromAllocation`), so it is a valid `LD_PRELOAD` target — unlike ONNX's fully-inlined case.

The catch: this internal function doesn't take a flat `(void*, size_t)` buffer like `TfLiteModelCreate` does. It takes ownership of a `std::unique_ptr<Allocation>`, an internal TFLite abstraction over a memory region. `tflite_model_create_hook_cxx.cpp` reads the buffer through `Allocation`'s public `base()`/`bytes()` accessors before forwarding the (moved, unconsumed) allocation to the real function, using the same `__asm__("mangled_name")` symbol-binding technique as the OpenVINO hook.

**This hook is validated end-to-end.** Build and run it with:

```bash
make hook-cxx-experimental
LD_PRELOAD=../build/tflite_model_create_hook_cxx.so ../build/infer_tflite ../models/model.tflite.enc <password>
```

Confirmed output:
```
[HOOK C++] VerifyAndBuildFromAllocation intercepted, 635656 bytes
[HOOK C++] Model dumped to ../models/dumped_model_cxx.tflite
Model loaded
Inference OK
```
`../models/dumped_model_cxx.tflite` is produced, identical in size to the decrypted buffer (635656 bytes), and inference completes with no visible disruption to the victim process.

The broader lesson, useful beyond TFLite specifically: **whether a C++ API can be hooked depends on how that specific function was compiled** (inlined away vs. genuinely exported), not on whether it's "C++" in general — which is exactly why the primary, most reliable target across all four frameworks in this toolkit is always the stable, documented, low-level API (a plain C function or C API struct), rather than a C++ convenience wrapper around it. The C++ hook here is a secondary confirmation of the same underlying weakness, not a replacement for the primary one.

The exact mangled symbol name is version-specific. If TensorFlow is updated, re-verify it with:
```bash
nm -D ~/Downloads/tflite_build/libtensorflow-lite.so | grep VerifyAndBuildFromAllocation
```
