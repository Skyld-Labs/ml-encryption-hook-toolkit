# QNN (Qualcomm AI Runtime) Hook

Implementation of the ML encryption hook for Qualcomm's AI Engine Direct (QNN) runtime, part of the QAIRT SDK.

## Overview

QNN is structurally different from the other three frameworks in this toolkit. TensorRT, OpenVINO, and ONNX Runtime all load a serialized model directly at inference time — encrypt the file, decrypt it in RAM, hand the buffer to a "load from memory" API. QNN instead requires a multi-stage **ahead-of-time conversion pipeline** before anything resembling "inference" exists:

```
model.onnx  →  patched ONNX  →  QNN IR (.cpp + .bin)  →  model lib (.so)  →  context binary (.bin)
```

Only the last artifact — the **context binary** — is the runtime-loadable object analogous to `model.onnx.enc` or a TensorRT engine file. It is what gets encrypted, and `QnnContext_createFromBinary()` — the QNN API that deserializes it — is the hook target.

This also means QNN has two distinct deployment shapes:

| Pipeline | Output | Hookable? |
|---|---|---|
| **Model library** (`qnn-model-lib-generator`) | Graph compiled directly into native code inside a `.so` | ❌ No buffer to intercept — same structural dead end as the ONNX C++ wrapper in `onnx/` |
| **Context binary** (`qnn-context-binary-generator`) | Serialized graph, loaded at runtime via a function table | ✅ `QnnContext_createFromBinary()` is resolved dynamically — hookable |

This toolkit targets the context binary pipeline.

## Requirements

- Linux x86_64 (tested on Ubuntu 24.04)
- **Qualcomm AI Runtime (QAIRT) SDK**, direct-download build (no Qualcomm ID needed) — version `2.29.0.241129` used here, downloaded from [qualcomm.com/developer/software/qualcomm-ai-engine-direct-sdk](https://www.qualcomm.com/developer/software/qualcomm-ai-engine-direct-sdk)
- **Python 3.10** specifically — the converter's native extension (`libPyIrGraph`) is ABI-locked to this version. Ubuntu 24.04 ships 3.12 by default, so a separate venv is required:
  ```bash
  sudo add-apt-repository ppa:deadsnakes/ppa
  sudo apt update && sudo apt install python3.10 python3.10-dev python3.10-venv
  ```
- `clang-14` (or `clang-16`) — `qnn-model-lib-generator` looks for a `clang++` binary on `PATH`, but Ubuntu only ships versioned binaries:
  ```bash
  sudo apt install clang-14
  ```
- OpenSSL development headers (`libssl-dev`) for the encrypt/decrypt/hook C++ code

No Snapdragon hardware is required. QNN ships an x86-compatible reference backend (`libQnnCpu.so`, `libQnnGpu.so`) specifically for host-side development and testing — see [Backend note](#why-the-gpu-backend-and-not-cpu) below for why this toolkit uses the GPU one.

## Setup

Extract the QAIRT SDK anywhere, then from `qnn/`:

```bash
export QNN_SDK_ROOT=/path/to/qairt/2.29.0.241129   # adjust if you didn't use the default in install_requirements.sh
source ./install_requirements.sh
```

`install_requirements.sh` must be **sourced**, not executed — it exports `QNN_SDK_ROOT`, `PATH`, `LD_LIBRARY_PATH`, activates the Python 3.10 venv, and creates a `clang++` shim. All of these need to persist in your current shell. Run it again at the start of every new terminal session before touching `make`.

## Build & run (via Makefile)

All commands below are run from `qnn/src`:

```bash
make all           # runs the full pipeline: patch → convert → compile-lib → context-binary → compile hook/infer/compile_qnn
make run-baseline  # encrypts the context binary, runs inference normally (no attack)
make run-attack    # encrypts, runs the attack, dumps the stolen context binary, diffs it against the original
make clean         # removes all generated artifacts (build/ contents, models/model_patched.onnx, models/dumped_*)
```

Override the password or the input model:

```bash
make run-attack PASSWORD=yourpassword MODEL=../models/other_model.onnx
```

## What each target does

- **`patch-onnx`** (`patch_onnx.py`): `qnn-onnx-converter` only supports the pre-opset-14 default for the Reshape operator's `allowzero` attribute (`allowzero=0`). Models exported with opset 14+ frequently set `allowzero=1`, which the converter rejects outright. This stage force-sets it back to 0 on every Reshape node before conversion.
- **`convert`** (`qnn-onnx-converter`): converts the patched `.onnx` into QNN's intermediate representation — a `.cpp` file that composes the graph via QNN API calls, plus a `.bin` holding the weights.
- **`compile-lib`** (`qnn-model-lib-generator`): compiles `model.cpp` + `model.bin` into `libmodel.so`, targeting `x86_64-linux-clang`.
- **`context-binary`** (`qnn-context-binary-generator`): loads `libmodel.so` against a QNN backend and serializes the finalized graph into `model_context.bin` — the actual artifact this toolkit attacks.
- **`compile_qnn`**: encrypts `model_context.bin` with AES-256-ECB (same pattern as every other framework in this repo — key derived from password via SHA-256).
- **`infer_qnn`**: the victim program. Decrypts the context binary in RAM, loads the QNN backend via `dlopen`, resolves the `QNN_INTERFACE` function table, and calls `QnnContext_createFromBinary()` on the decrypted buffer.
- **`qnn_context_hook.so`**: the `LD_PRELOAD` library used in `make run-attack`.

## Troubleshooting / Quirks

- QNN requires Python 3.10 and the QAIRT SDK; if the pipeline fails, verify that the correct venv is active.
- The GPU backend is required for context binary generation on x86; the CPU backend does not support context caching for this demo.
- If `qnn-onnx-converter` rejects the model, rerun `patch_onnx.py` to fix `Reshape` `allowzero` attributes.

## How the hook works

Unlike the other three frameworks, QNN doesn't expose a single stable entry-point symbol comparable to ONNX Runtime's `OrtGetApiBase()`. The `QNN_INTERFACE` function table (which holds `contextCreateFromBinary` among dozens of other functions) is obtained by calling `QnnInterface_getProviders()` — a symbol resolved by the *victim itself* via `dlsym()` on the backend library it just `dlopen`'d.

This means the hook can't patch a well-known exported symbol directly. Instead, `qnn_context_hook.cpp` intercepts **`dlsym()` itself**:

1. The hook re-exports `dlsym()`, resolving the real one via `dlvsym(RTLD_NEXT, "dlsym", "GLIBC_2.2.5")` (using `dlvsym` with an explicit glibc version, rather than plain `dlsym(RTLD_NEXT, ...)`, avoids ambiguity between symbol versions and sidesteps recursive self-interception).
2. Every call to `dlsym()` is passed through transparently — *except* when the requested symbol is `"QnnInterface_getProviders"`. In that one case, the hook returns a pointer to its own wrapper (`hooked_getProviders`) instead of the real function.
3. When `infer_qnn` calls what it thinks is `QnnInterface_getProviders()`, it actually gets `hooked_getProviders()`. This wrapper calls the *real* `QnnInterface_getProviders()` first (to get the genuine provider list), then patches the `contextCreateFromBinary` function pointer inside that provider's `QNN_INTERFACE_VER_NAME` struct — saving the original pointer and substituting the hook's own function.
4. From that point on, whenever `infer_qnn` calls `contextCreateFromBinary()` through the (now-patched) interface struct, it silently runs `hooked_contextCreateFromBinary()` first: this dumps the decrypted buffer to `../models/dumped_model_context.bin`, then forwards the call to the real function so inference proceeds normally.

This is a different interception layer than any other framework in this toolkit (vtable patch for TensorRT, mangled-symbol resolution for OpenVINO, direct C API struct patch for ONNX Runtime) — here the hook has to intercept the *symbol resolution mechanism itself*, because the function table isn't reachable through a single well-known exported entry point.

### Why the GPU backend, and not CPU

`libQnnCpu.so` — QNN's reference CPU backend, meant for host-side testing without Snapdragon hardware — does not support context binary caching at all; attempting `qnn-context-binary-generator` against it fails with `Context caching is not supported by current backend`. `libQnnGpu.so` does support it and runs correctly on a standard x86 GPU (or software rasterizer, if no dedicated GPU is present), which is why `BACKEND_SO` in the Makefile points there instead. This is purely a backend capability limitation on x86 — the hook itself targets `contextCreateFromBinary()` regardless of which backend is loaded, so the same interception would apply unchanged on real Snapdragon/HTP hardware.

After running:

