# TensorRT Hook

Reference implementation of the ML encryption hook for TensorRT models.

## Overview

This directory contains the canonical implementation of the encryption hook mechanism. It serves as the reference for implementing hooks in other frameworks (ONNX, OpenVINO, TFLite).

## Structure

```
tensorrt/
├── README.md                     # This file
├── install_requirements.sh       # Verifies TensorRT/CUDA are present, installs the rest
├── src/                            # All source code and the build system
│   ├── Makefile
│   ├── compile.cpp               # Builds a TensorRT engine from ONNX, then encrypts it (AES-256-ECB)
│   ├── infer.cpp                 # Loads the encrypted engine, decrypts it in memory, runs inference
│   └── trt_deserialize_hook.c    # LD_PRELOAD hook that dumps the decrypted engine before TensorRT uses it
├── build/                          # Compiled binaries (generated, not tracked by git)
│   ├── compile
│   ├── infer
│   └── trt_deserialize_hook.so
└── models/                         # All model files, at every stage (kept in git via .gitkeep)
    ├── .gitkeep
    ├── model.onnx                 # Input model (source, not versioned)
    ├── model.engine.enc            # Encrypted engine (generated)
    └── dumped_model.engine         # Stolen engine (generated by the attack)
```

`src/` holds only code, `build/` holds only compiled binaries (git-ignored), and `models/` holds every model artifact — regardless of which stage produced it. `models/.gitkeep` keeps the empty folder tracked in git even before any artifact has been generated.

## Requirements

- Linux (tested on Jetson, aarch64)
- `g++` / `gcc` with C++17 support, and `make`
- NVIDIA TensorRT (`libnvinfer`, `libnvonnxparser`) and headers — comes with the JetPack SDK, not installable via `apt`/`pip`
- CUDA toolkit (`cudart`) — also comes with JetPack
- OpenSSL development headers (`libssl-dev`, provides `libcrypto`)

Run the install script from the `tensorrt/` directory to check for TensorRT/CUDA and install the remaining dependencies:

```bash
./install_requirements.sh
```

TensorRT and CUDA themselves can't be installed by this script (they're provisioned by NVIDIA SDK Manager as part of JetPack) — it verifies they're present at the expected paths and tells you where to look if not, then installs `libssl-dev` and build tools.

On Jetson, header/library paths may differ from a standard install. If paths differ from the defaults, adjust `TRT_INC`/`TRT_LIB` at the top of `src/Makefile` accordingly (e.g. if CUDA is at `/usr/local/cuda-12.6/targets/aarch64-linux/include` vs. a different version).

## Build & run (via Makefile)

All commands below are run from `tensorrt/src`. Compiled binaries are placed in `../build`, which is git-ignored.

```bash
make all           # compiles compile, infer, and the hook into ../build
make run-baseline  # encrypts ../models/model.onnx, runs inference normally (no attack)
make run-attack    # encrypts the model, runs the attack, dumps the stolen engine to ../models/
make clean         # removes ../build entirely
```

Override the password or the input model without editing the `Makefile`:

```bash
make run-attack PASSWORD=yourpassword MODEL=../models/other_model.onnx
```

### What each target does

- **`compile`**: builds a TensorRT engine from `model.onnx`, encrypts it with AES-256-ECB, and writes it to `../models/model.engine.enc`.
- **`infer`**: reads `model.engine.enc`, decrypts it in RAM, and calls `runtime->deserializeCudaEngine(blob, size)` to load and run inference — this is the legitimate, non-hooked path.
- **`trt_deserialize_hook.so`**: the `LD_PRELOAD` library used in `make run-attack`. It intercepts `deserializeCudaEngine` and dumps the decrypted engine to `../models/dumped_model.engine` before letting the real function proceed.

## Troubleshooting / Quirks

- `IDX_DESERIALIZE` is version-dependent; if the hook does not intercept, rederive the vtable index for your TensorRT version.
- Ensure TensorRT and CUDA headers/libraries are visible to the `Makefile` paths.
- If the victim crashes, confirm the `LD_PRELOAD` hook is loaded and the real `deserializeCudaEngine` symbol is still available.

## Manual build (if you're not using `make`)

```bash
cd src
mkdir -p ../build

g++ compile.cpp -o ../build/compile \
    -I/usr/include/aarch64-linux-gnu \
    -I/usr/local/cuda-12.6/targets/aarch64-linux/include \
    -L/usr/lib/aarch64-linux-gnu \
    -L/usr/local/cuda-12.6/targets/aarch64-linux/lib \
    -lnvinfer -lnvonnxparser -lcudart -lcrypto

g++ -std=c++17 infer.cpp -o ../build/infer \
    -I/usr/include/aarch64-linux-gnu \
    -I/usr/local/cuda-12.6/targets/aarch64-linux/include \
    -L/usr/lib/aarch64-linux-gnu \
    -L/usr/local/cuda-12.6/targets/aarch64-linux/lib \
    -lnvinfer -lcudart -lcrypto

gcc -shared -fPIC trt_deserialize_hook.c -o ../build/trt_deserialize_hook.so \
    -I/usr/include/aarch64-linux-gnu -ldl
```

## Run manually, step by step

```bash
cd src
mkdir -p ../models   # first run only

../build/compile ../models/model.onnx model.engine.enc <password>
../build/infer ../models/model.engine.enc <password>
LD_PRELOAD=../build/trt_deserialize_hook.so ../build/infer ../models/model.engine.enc <password>
```

The decrypted engine is dumped to `../models/dumped_model.engine`, byte-for-byte identical to the in-memory decrypted buffer — despite the on-disk file being encrypted.

## How it works

1. `infer` reads the encrypted `.engine` file and decrypts it in RAM (AES-256-ECB, key derived from the password via SHA256).
2. It calls `runtime->deserializeCudaEngine(blob, size)` to load the decrypted buffer into TensorRT.
3. `deserializeCudaEngine` is a C++ virtual method. The hook intercepts the exported `createInferRuntime_INTERNAL` symbol via `LD_PRELOAD`, locates the internal implementation object's vtable, and overwrites the function pointer for `deserializeCudaEngine` with its own function.
4. When `infer` later calls `deserializeCudaEngine`, the hook's function runs first: it dumps the decrypted buffer to disk, then forwards the call to the real function so the program behaves normally and the victim notices nothing.

### Finding `IDX_DESERIALIZE` for your TensorRT version

Unlike the OpenVINO hook (a mangled C++ symbol that can be resolved directly with `nm -D`) or the ONNX Runtime hook (a named field in a public C API struct), the vtable slot used by `deserializeCudaEngine` has no name or public symbol to look up — it's just an offset into an array of function pointers. `IDX_DESERIALIZE = 3` in `trt_deserialize_hook.c` was found empirically for the specific TensorRT build this toolkit was tested against, and is **not guaranteed to be correct for other versions**. If the hook segfaults or never prints `[HOOK] ENGINE HOOKED`, re-derive the index for your setup with either of the following approaches.

**Option A — brute-force scan (simplest, no debugger needed)**

Since the hook already prints `[HOOK] ENGINE HOOKED` when it fires, and `deserializeCudaEngine` is always called exactly once per `infer` run, you can just try each plausible index in turn:

```bash
for i in 0 1 2 3 4 5 6 7 8; do
    sed -i "s/#define IDX_DESERIALIZE .*/#define IDX_DESERIALIZE $i/" trt_deserialize_hook.c
    make -B ../build/trt_deserialize_hook.so
    echo "--- Trying index $i ---"
    LD_PRELOAD=../build/trt_deserialize_hook.so ../build/infer ../models/model.engine.enc <password> 2>&1 | grep -E "HOOK|Segmentation|Inference OK"
done
```

The correct index is the one that prints `[HOOK] ENGINE HOOKED` **and** completes with `Inference OK` (not a crash) — a wrong index will either do nothing (the real `deserializeCudaEngine` runs unmodified, no `[HOOK]` line) or segfault (you overwrote an unrelated function pointer with an incompatible signature).

**Option B — inspect the vtable call directly with GDB**

More precise, useful if the brute-force range above doesn't cover the right slot:

```bash
gdb --args ../build/infer ../models/model.engine.enc <password>
(gdb) break deserializeCudaEngine
(gdb) run
(gdb) disassemble
```

Look for an indirect call through the object's vtable, typically of the form `call *N(%rax)` or `call QWORD PTR [rax+N]`. The byte offset `N` divided by 8 (pointer size on 64-bit) gives the vtable index — e.g. `call QWORD PTR [rax+0x18]` corresponds to `IDX_DESERIALIZE = 0x18 / 8 = 3`. Note that `IRuntime::deserializeCudaEngine` (the public entry point you break on) may itself just forward to the internal `mImpl` object's own vtable — if the disassembly shows a call to another function rather than a direct vtable dispatch, step into it (`stepi` / `si`) until you reach the actual indirect call.

Once you have the right index, update `IDX_DESERIALIZE` in `trt_deserialize_hook.c` and rebuild with `make clean && make all`.
