# ONNX Runtime Hook

Implementation of the ML encryption hook for ONNX Runtime models.

## Overview

This directory contains the ONNX Runtime-specific implementation of the encryption hook mechanism, based on the TensorRT reference implementation.

Unlike TensorRT (which loads a prebuilt engine directly) and OpenVINO (which requires converting to IR first), ONNX Runtime loads `.onnx` bytes directly — no intermediate conversion is needed, which makes this the simplest pipeline of the four frameworks in this toolkit. The encrypted model is decrypted in memory and loaded directly into ONNX Runtime.

## Structure

```
onnx/
├── README.md                    # This file
├── install_requirements.sh      # Installs ONNX Runtime + OpenSSL dev headers
├── src/                         # All source code and the build system
│   ├── Makefile
│   ├── compile_onnx.cpp         # Encrypts a raw .onnx file (AES-256-ECB)
│   ├── infer_onnx.cpp           # Loads the encrypted model, decrypts it in memory, runs inference
│   ├── onnx_session_hook.c      # LD_PRELOAD hook (C API) — the working attack, used by `make run-attack`
│   └── onnx_session_hook_cxx.cpp # Documented dead end: an attempt to hook the C++ API directly (see below)
├── build/                       # Compiled binaries (generated, not tracked by git)
│   ├── compile_onnx
│   ├── infer_onnx
│   └── onnx_session_hook.so
└── models/                      # All model files, at every stage (kept in git via .gitkeep)
    ├── .gitkeep
    ├── model.onnx                # Input model (source)
    ├── model.onnx.enc             # Encrypted model (generated)
    └── dumped_model.onnx          # Stolen model (generated by the attack)
```

`src/` holds only code, `build/` holds only compiled binaries (git-ignored), and `models/` holds every model artifact — original, encrypted, or stolen — regardless of which stage produced it. `models/.gitkeep` keeps the empty folder tracked in git even before any artifact has been generated.

## Requirements

- Linux x86_64 (tested on Ubuntu 24.04)
- `g++` / `gcc` with C++17 support, and `make`
- ONNX Runtime with C++ headers and libraries
- OpenSSL development headers (`libssl-dev`)

Run the install script from the `onnx/` directory to install everything above in one go:

```bash
./install_requirements.sh
```

This downloads and installs ONNX Runtime 1.20.0 into `/opt/onnxruntime`, then installs `libssl-dev` and `build-essential`.

If ONNX Runtime is installed elsewhere, adjust `ORT_ROOT` at the top of `src/Makefile` — everything else derives from that one variable.

## Build & run (via Makefile)

All commands below are run from `onnx/src`. The `Makefile` wraps every build and run step, including setting the necessary paths. Compiled binaries are placed in `../build`, which is git-ignored — nothing under `build/` should be committed.

```bash
make all           # compiles compile_onnx, infer_onnx, and onnx_session_hook.so into ../build
make run-baseline  # encrypts ../models/model.onnx, runs inference normally (no attack)
make run-attack    # encrypts the model, runs the attack, dumps the stolen model to ../models/
make clean         # removes ../build entirely
```

Override the password or the input model without editing the `Makefile`:

```bash
make run-attack PASSWORD=yourpassword MODEL=../models/other_model.onnx
```

`onnx_session_hook_cxx.cpp` is intentionally **not** built by `make all` — see "Why the C++ API can't be hooked the same way" below for why it's kept in the repo without being part of the working toolkit.

### What each target does

- **`compile_onnx`**: reads `model.onnx`, encrypts it with AES-256-ECB, and writes it to `../models/model.onnx.enc`.
- **`infer_onnx`**: reads `model.onnx.enc`, decrypts it in RAM, and calls `Ort::Session(env, model_data, model_data_length, options)` to load and run inference — this is the legitimate, non-hooked path.
- **`onnx_session_hook.so`**: the `LD_PRELOAD` library used in `make run-attack`. It intercepts `OrtApi::CreateSessionFromArray` and dumps the decrypted model to `../models/dumped_model.onnx` before letting the real function proceed.

## Manual build (if you're not using `make`)

```bash
cd src
mkdir -p ../build

g++ -std=c++17 compile_onnx.cpp -o ../build/compile_onnx \
    -I/opt/onnxruntime/include \
    -L/opt/onnxruntime/lib \
    -Wl,-rpath,/opt/onnxruntime/lib \
    -lonnxruntime -lcrypto

g++ -std=c++17 infer_onnx.cpp -o ../build/infer_onnx \
    -I/opt/onnxruntime/include \
    -L/opt/onnxruntime/lib \
    -Wl,-rpath,/opt/onnxruntime/lib \
    -lonnxruntime -lcrypto

gcc -shared -fPIC onnx_session_hook.c -o ../build/onnx_session_hook.so \
    -I/opt/onnxruntime/include -ldl
```

## Run manually, step by step

```bash
cd src
mkdir -p ../models   # first run only

../build/compile_onnx ../models/model.onnx <password>
../build/infer_onnx ../models/model.onnx.enc <password>
LD_PRELOAD=../build/onnx_session_hook.so ../build/infer_onnx ../models/model.onnx.enc <password>
```

The decrypted model is dumped to `../models/dumped_model.onnx`, byte-for-byte identical to the original `.onnx` file — despite the on-disk file being encrypted. Verify with:

```bash
diff ../models/dumped_model.onnx ../models/model.onnx
# (no output means the files are identical)
```

## How it works

1. `infer_onnx` reads the encrypted `.onnx.enc` file and decrypts it in RAM (AES-256-ECB, key derived from the password via SHA-256).
2. It constructs an `Ort::Session(env, model_data, model_data_length, options)`, the C++ wrapper's entry point for loading a model from an in-memory buffer. Internally, this calls the C API function `OrtApi::CreateSessionFromArray`.
3. ONNX Runtime exposes a stable, documented C API: `OrtGetApiBase()` is the single exported symbol, returning an `OrtApiBase*` whose `GetApi()` returns an `OrtApi*` — a plain struct of function pointers. This is a much more stable hook surface than a mangled C++ vtable (TensorRT) or a mangled symbol name (OpenVINO): the struct layout and field names are part of the public, versioned C API, so no version-specific symbol resolution is needed here.
4. The hook re-exports `OrtGetApiBase()` itself (via `LD_PRELOAD`), resolves the real one with `dlsym(RTLD_NEXT, "OrtGetApiBase")`, then patches the `CreateSessionFromArray` field of the returned `OrtApi` struct to point to its own function.
5. When `infer_onnx` later triggers `CreateSessionFromArray`, the hook's function runs first: it dumps the decrypted model buffer to disk, then forwards the call to the real function so the program behaves normally and the victim notices nothing.

### Why `RTLD_NEXT` instead of `dlopen`

An earlier version of the hook used `dlopen("libonnxruntime.so", ...)` + `dlsym` to resolve the real `OrtGetApiBase`. This is fragile in an `LD_PRELOAD` context: if the dynamic linker's search path doesn't happen to resolve the library name, `dlopen` can fail silently, leading to a NULL function pointer call (segfault) when the real function is invoked. `dlsym(RTLD_NEXT, ...)` is the correct tool for this: it asks the dynamic linker to resolve the symbol from the libraries loaded *after* this one in the process, i.e. directly from the real `libonnxruntime.so` already mapped into the process — no extra `dlopen` needed, and no dependency on library search paths.

## Why the C++ API can't be hooked the same way

`onnx_session_hook_cxx.cpp` is kept in this repository as a documented dead end, not as a working alternative to `onnx_session_hook.c`. It is not built by `make all`.

The reason it can't work is structural, not a matter of guessing the wrong symbol name: `Ort::Session`'s constructor is defined `inline`, directly inside `onnxruntime_cxx_inline.h`. An `inline` function's code is compiled directly into whatever binary includes that header — here, into `infer_onnx` itself — rather than being compiled once into `libonnxruntime.so` and called from there. As a result, there is no dynamically-resolved symbol call to `Ort::Session::Session(...)` for `LD_PRELOAD` to intercept: the mangled constructor names the hook searches for (`_ZN3Ort7SessionC1E...` and its variants) simply don't exist as exported symbols in `libonnxruntime.so`, and depending on optimization the call may even be fully inlined away inside `infer_onnx` with no separate call at all.

This is a useful illustration for understanding the attack surface in general: what matters is not which API a developer *writes against*, but where the corresponding code actually executes at runtime. `OrtApi::CreateSessionFromArray` is hookable because it is a real, dynamically-dispatched call into a separate shared library. The C++ wrapper around it is not, because it's just a convenience layer that gets compiled away into the caller.
